# MPF Pod Alert System

**Pod Alert** — система термінового виклику трейдерів поду. Трейдер у Discord вводить `/trader`, обирає колег, і на їхні iPhone приходить **критичне** сповіщення Bark, яке пробиває беззвучний режим і повторює звук.

Зараз система працює як воркфлоу **n8n**. Цей репо містить повний експорт воркфлоу без секретів, ту саму логіку у вигляді чистого JS (`core/`) і документацію, за якою систему можна перенести на **Cloudflare Worker** без участі автора.

> **Для агента (Claude Code), який приймає систему.** Джерело істини — `n8n/workflow.json` і `POD-ALERT-FULL-CODE.md`. `workflow.json` відтворено з живого експорту без секретів і службових ID інстансу: код і параметри нод ідентичні бойовим, але імпорт у n8n не перевірявся, бо ТЗ забороняло щось змінювати в n8n. `core/` повторює поведінку n8n 1:1, включно з неочевидними місцями та двома відомими дефектами: їх не виправлено навмисно. Суттєва відмінність одна: повтори запитів на Bark. У `core/` вони поштучні за рішенням власника, а в n8n повторюється вся нода, і це дає дублікати. Повний перелік платформних відмінностей — `docs/ARCHITECTURE.md` → «Розбіжності `core/` ↔ n8n». Власник підтвердив: поточна поведінка n8n — чинна логіка системи. Усі значення, доступи й рішення дає він (`docs/WORKER-MIGRATION.md`, «Хто що дає»). Перед перенесенням прочитай `docs/ARCHITECTURE.md` (розділи «Неочевидна поведінка» і «Відомі дефекти») та `docs/WORKER-MIGRATION.md`.

## Для кого

- **Трейдери поду** (5 людей у конфігу): викликають одне одного в Discord-канал, коли потрібна термінова увага.
- **Людина, яка обслуговує систему**, і її агент: розгортання, перенесення, зміна складу трейдерів.

## Як це працює (фактична поведінка)

1. **Виклик.** Трейдер вводить slash-команду `/trader`. Discord надсилає interaction (POST) на вебхук n8n `{{N8N_BASE_URL}}/webhook/pod-alert`.
2. **Перевірка підпису.** Кожен запит перевіряється за Ed25519 публічним ключем застосунку: `crypto.verify` з SPKI/DER-обгорткою в n8n, Web Crypto у `core/`. При невірному підписі відповідь `401`. Discord навмисно шле такі запити, коли зберігаєш Interactions Endpoint URL, і без 401 endpoint не приймається. Службовий PING (`type: 1`) отримує PONG `{"type":1}`.
3. **Тихі години.** На команду `/trader` спершу йде перевірка часу: з **22:00 до 08:00 за Києвом** (`Intl.DateTimeFormat`, `Europe/Kyiv`, з урахуванням літнього часу) трейдер отримує ефемерне повідомлення «Нічний режим…», і меню не показується. Перевірка стоїть **лише на кроці показу меню**: вибір у вже відкритому меню після 22:00 сигнал надішле. PING і перевірку підпису тихі години не блокують.
4. **Вибір адресатів.** Трейдер бачить ефемерне повідомлення «Кого викликати?» з select-меню всіх трейдерів з конфігу (від 1 до всіх). **Того, хто викликає, система не виключає**: він є в меню і може вибрати себе. `callerId` обчислюється, але не використовується.
5. **Перевірка каналу.** Коли трейдер робить вибір, перевіряється, що взаємодія відбулась у дозволеному каналі (`allowedChannel`). Інакше прийде відповідь «Команда доступна лише у визначеному каналі». Саме меню показується в будь-якому каналі, де Discord дозволяє команду. Основне обмеження каналу задається правами команди в Discord, а ця перевірка додаткова.
6. **Відповідь і доставка.** Discord одразу отримує ефемерне «Сигнал надіслано: trader2, trader3». **Після** цього на кожного адресата йде окремий `POST {{BARK_SERVER_URL}}/push` (3 спроби, пауза 5 с). На iPhone приходить критичне сповіщення з посиланням на Discord-канал.

Конфіг — одна нода-довідник (`Pod alert config`). Для кожного трейдера там задано ключ пристрою Bark, Discord ID (у логіці не використовується), звук, гучність, рівень (`critical`) і повтор звуку (`call`). Там же адреса Bark-сервера, ID застосунку, публічний ключ, сервер, дозволений канал, текст сповіщення, а посилання на канал збирається з ID сервера і каналу.

Детально — `docs/ARCHITECTURE.md`.

```
n8n/nodes/*.js             код кожної Code-ноди, назва файлу = назва ноди

  verify-signature.js      verifySignature(): Ed25519 через crypto.subtle
  quiet-hours.js           checkQuietHours(now)
  interactions.js          handleInteraction(cfg, sig, now) → { response, pushes }
  bark.js                  buildBarkRequest(item), sendBark(item) з повторами
  package.json             {"type":"module"}, щоб core/ запускався в Node без бандлера
docs/ARCHITECTURE.md       тригер, граф нод, дані звідки/куди, неочевидна поведінка, дефекти

reports/export-report.md   звіт про вивантаження
```

## Зовнішні залежності

| Що | Де живе | Чи переїжджає на Worker |
|---|---|---|
| Discord-застосунок зі slash-командою `/trader` | Discord Developer Portal | Ні. Міняється лише Interactions Endpoint URL |
| Bark-сервер (`/push`) | Окремо: Docker на VPS за Caddy | **Ні**, див. нижче |
| Застосунок Bark на iPhone кожного трейдера | Телефони | Ні |
| n8n-воркфлоу | `{{N8N_BASE_URL}}` | Так, це те, що переноситься |

### Bark-сервер: доступність (перевірено)

Перевірено 2026-11-03 зовні, з IP, що не належить VPS n8n. Сам Caddyfile не переглядався, бо доступу до VPS немає. Висновок зроблено за поведінкою сервера, нічого не змінювалось:
- `GET /ping`, `/healthz`, `/info` → `200`, заголовки `server: Caddy` + `server: Bark`, bark-server **v2.3.7**;
- `POST /push` з неіснуючим device key → `400 failed to get device token` від самого Bark. Тобто запит пройшов Caddy і дійшов до bark-server (сповіщення не надсилалось);
- **обмежень за IP немає, HTTP-автентифікації (basic auth тощо) немає**, ні на службових шляхах, ні на `/push`. Єдиний захист `/push` — секретність device keys.

Для перенесення: Worker зможе слати на існуючий сервер без змін на Caddy (варіант А). Побічне спостереження: `/info` публічно показує версію і кількість зареєстрованих пристроїв. Для Bark це стандартна поведінка, на роботу системи не впливає.

### Bark-сервер: два варіанти

- **А. Використати існуючий Bark-сервер** (рекомендовано, якщо власник згоден). Worker шле на ту саму адресу `BARK_SERVER_URL`, а ключі пристроїв лишаються ті самі. Потрібно отримати від власника адресу сервера і 5 device keys.
- **Б. Підняти власний Bark-сервер.** Docker-образ `finab/bark-server` за HTTPS-проксі (Caddy, nginx і т. ін.). **Ключі пристроїв прив'язані до сервера**, тому кожен трейдер має додати новий сервер у застосунку Bark і передати свій новий device key. Деталі — `docs/INTEGRATIONS.md`.

## Перенесення на Cloudflare Worker: коротко

Повний план з поясненнями — `docs/WORKER-MIGRATION.md`. Коротко:

1. Отримати секрети (`SECRETS.md`) і визначитись із Bark-сервером (варіант А чи Б).
2. Створити Worker і записати секрети через `wrangler secret put …`.
3. У `fetch(request, env, ctx)`: прочитати `await request.text()` і заголовки підпису → `verifySignature` → `handleInteraction` → повернути `response` → `ctx.waitUntil(Promise.allSettled(pushes.map(p => sendBark(p, fetchWithTimeout))))`. ⚠️ Не пишіть `pushes.map(sendBark)`: `map` передасть index і масив як `fetchImpl`/`sleep`, і всі запити тихо впадуть. Повний орієнтир — у WORKER-MIGRATION.md.
4. Задеплоїти, перевірити PING (Discord сам перевіряє endpoint при збереженні URL).
5. У Discord Developer Portal → General Information → **Interactions Endpoint URL** вказати адресу Worker і зберегти.
6. Перевірити `/trader` удень і вночі, вибір у дозволеному й іншому каналі.
7. Вимкнути n8n-воркфлоу (після того, як Discord перейшов на Worker).

## Безпека

- У репо немає жодного справжнього ключа чи ID: усе замінено на `{{NAME}}` (список — `SECRETS.md`).
- Нікнейми трейдерів замінено на `trader1…trader5`. Хто з них хто, знає власник системи.
- У n8n секрети зберігались прямо в Code-ноді. У Worker їх треба тримати лише в Secrets (`wrangler secret put`), не в коді і не в `wrangler.toml`.
